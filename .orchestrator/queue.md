  **90b. ⛔ THREE QUESTIONS FOR THE USER — all pure feel, which the harness explicitly cannot verify, so none is the orchestrator's to answer.** Each carries a recommendation; answering is a one-word edit to this item, after which S5 and S7 dispatch. S0–S4 and S6 need none of them and could be dispatched first if a slot frees before these are answered.

  **Q1 — what is a wheel notch (real mouse) worth?** Today `WHEEL_LINES_PER_NOTCH = 3.0` ROWS, which is exactly why one notch over a tall image was worth the entire image. (a) **RECOMMENDED — 3 × base line height, as a pixel distance** (~154 physical px at today's default, still derived from line height so zoom keeps scaling it): preserves the mouse feel exactly over ordinary text, where every row is the base height, while the continuous position stops it swallowing an image. (b) A fixed physical pixel constant: consistent across zoom, but decouples scrolling from the text's rhythm. (c) A viewport fraction (~15% of visible height): scales with window size, but is the biggest departure and reads fast on large displays.

  **Q2 — does Page Up/Down become a viewport move, or stay a caret mover?** The item's SCOPE sentence says convert it. (a) **RECOMMENDED — DROP Page Up/Down from this item; Page stays a caret mover**, and item 90 routes only the two existing screenful ESTIMATES through one `viewport_avail_px` owner, which closes the live-vs-headless page divergence (`keys.rs:259` measured screenful vs `main/run.rs:545-558` fixed 20 logical lines). Converting Page is a genuine product change — it touches the recoil contract, the overlay arm and the diff-preview arm, and CLAUDE.md records "Shift-PageDown/PageUp deliberately do not extend a selection" as SETTLED precisely because Page is a mover — so it earns its own item rather than riding along inside a representation migration. (b) Convert it now as the SCOPE sentence says, accepting that the settled divergence gets reopened here. If (a), amend the SCOPE sentence when this lands.

  **Q3 — trackpad gain. This is the biggest feel delta in the item and the one most worth the user's hands.** Today `WHEEL_PIXELS_PER_LINE = 16.0` physical px per visual ROW, against a ~51.2 physical px row at the live macOS default — so trackpad scrolling is currently **~3.2× AMPLIFIED**. Feeding raw `PixelDelta` in makes it 1:1, i.e. **3.2× SLOWER than the hands currently expect**, on the very gesture this item exists to improve. (a) **RECOMMENDED — 1:1 physical pixels**: what native macOS apps do, what SCOPE's "real trackpad deltas" literally means, and it incidentally fixes today's zoom/DPI-dependent scroll speed. (b) Keep today's ~3.2× behind a named `TRACKPAD_GAIN`: no feel change, but the constant is a fudge factor with no principled value and speed stays DPI-dependent unless expressed in row heights. (c) Ship 1:1 as the default but expose `TRACKPAD_GAIN` as a config dial, so this can be settled live by turning one value instead of a rebuild. **Whichever is chosen, the implementer must report it LIVE-ONLY and must NOT claim the feel verified.**
