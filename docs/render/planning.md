# Scene planning

Read before changing the scene planner, its geometry ownership, or work bounds.

[Guide](../render.md) · Paths in code examples are relative to the repo root.

## The scene planner (`render/plan/`) — item 174

- **ONE deterministic, device-free layout stage between the measured inputs and the GPU.** It consumes the `ViewState` projection (the pipeline's `overlay_*` mirror), the already-resolved card box, the overlay row pitch and the grouped display-line sequence, and emits INSPECTABLE primitives plus INTERACTION geometry: one `PlannedRow { display, item, top, height }` per candidate DISPLAY LINE, `row_at(px, py)`, `display_at(py)`, `selected_display()`, `content_rows()`/`footer_top()`. It shapes nothing, measures nothing, reads no clock and touches no wgpu — so presentation decisions are assertable without a device (`render/plan/tests.rs`).
- **THE FORWARD `row -> y` ARITHMETIC AND ITS INVERSE ARE PRIVATE TO `plan/overlay_rows.rs`.** `overlay_row_top`, `overlay_row_of` and `overlay_row_index` are gone from `render/chrome`: a consumer cannot re-derive a row's position, only read it off the plan the pixels came from. Held by `render/tests/overlay_plan_law.rs`'s `only_the_planner_derives_an_overlay_row_position` — sentinels for the retired call names, `header_rows as f32`, AND for stepping off the band origin (`first_top` × a row count), which is the shape that hid `livingband::covered_rows`' own grid and the footer plate's seat for two years.
- **Routed through the one plan** (built once per overlay frame in `prepare_overlay`, threaded down): the pointer hit-test (`overlay_row_at`), the range rails (draw + hit), the visual-selection transaction's band target and coverage grid, the Pane band, the `Bars` plates, the chord plates, the footer plate, the slant text-clip bands, the shaped rows' item mapping, and the sidecar's `overlay.window` report. Item 164's arrangement is preserved: the planner is the one owner of `selected_display()`, `resolve_visual_selection` is still the only render path that reads it (`visual_selection_law`'s no-wildcard source sweep), and `overlay_row_at` deliberately stays outside the transaction.
- **The inverse SCANS the planned slots, it does not invert the formula.** `(py - first_top) / lh` truncated at a row's own first pixel lands on the row ABOVE whenever `k * lh` is not exactly representable (found at `lh = 12`, `header_gap = 63.55`, row 11). Comparing against the same `f32` tops the band was drawn from cannot disagree with the draw. O(visible) over at most a couple of dozen rows.
- **O(visible), never O(doc), and never retained.** One `PlannedRow` per display line the card shows — a 40,000-row Go-to picker plans the twelve on screen (384 bytes for the palette's 106-item catalog). There is no plan cache, so there is no key to go stale and no `buffer.version()` collision can serve a stale band; `the_plan_is_rederived_across_resize_zoom_and_a_buffer_swap` proves the absence is real. The planner counts its own work (`plan::plan_witness`), and `--bench-suite`'s `palette` cell asserts the exact per-frame plan count plus the O(visible) bound.
- **HOW MANY PLANS ONE FRAME IS ENTITLED TO (item 217) — every pass NAMED, never a number.** `prepare_overlay` used to build the row plan TWICE, unconditionally on every world: once up front and once again after `resolve_diagonal_cluster`, because a measured diagonal cluster changes the plan's `dx`/`dw` and the cluster is derived from rows shaped against that very plan. That cycle is now broken the other way — the frame builds ONE plan and COMPLETES it in place (`OverlayRowPlan::complete_row_extent`, whose arithmetic is the same `apply_row_extent` a fresh build runs, so completing lands exactly where rebuilding did). The one remaining second plan belongs to item 51's RIGHT-ANCHORED content-hug measurement, which shapes a PROVISIONAL card inside `set_view` to learn how wide to hug and so cannot be the frame's plan at all. The witness (`benchsuite::FramePasses`, one owner shared by the bench cell and `render/tests/plan_pass_law.rs`) names both and asserts their sum, so a THIRD plan still fails by name; its content-hug oracle reads the measurement's own cached width rather than the anchor predicate the pipeline branches on. **The axis that mattered was the card ANCHOR, not the list style** — the diagonal world Magpie (top-LEFT) plans once and the upright poster world Cassowary (top-RIGHT) plans twice.
- **`content_rows` is the one owner of "how many display lines precede the footer"** — the candidate band PLUS an empty-state notice. It used to be the grouped family's plan length alone, omitting the notice line the card height had already paid for, so a `Bars` world's picker filtered to zero matches drew its footer plate over the "no matches" row. Three-arm law over the whole shipping `Bars` roster (`an_empty_states_notice_row_carries_no_footer_plate_on_any_bare_plate_world`): the emitted quads may not overlap the notice row's planned slot; where an absolute pixel oracle can see the plate at all, the notice band must read as card ground; and the two plateless bare-plate worlds must emit no row surface at all (item 236).
- **THE HEADER BAND (the SECOND family, 2026-08-02).** The two display lines ABOVE the candidate band — the query/title INPUT field every takeover picker draws, and the grouped family's lens STRIP — are planned by the same code, as `PlannedHeader { line, top, height }`. Header line `i` sits at `text_top + i*lh` and is `lh` tall EXCEPT the last, which is `lh + header_gap`: the query BEAT is STRUCTURAL and lives inside the last header line's own box (the shaper inflates that line's real glyph metrics by it — `shape_overlay_names`'s `header_lh`, `shape_theme_spans`'s `strip_lh`), never as a blank line between boxes. So the band tiles from `text_top` down to `plan.first_top()` with no hole and no overlap, by construction. **FOUR `render/chrome` owners were DELETED, not banned by law:** `overlay_secondary_top` → `OverlayRowPlan::secondary_top`, `overlay_split_bounds` → `OverlayRowPlan::split_bounds`, `overlay_strip_band` → `OverlayRowPlan::strip_band`, `overlay_query_center` → `PlannedHeader::center`. The shaper's own `header_lh` READS the planned box rather than re-summing beside it, so the DRAWN box and the planned one are literally one object; `right_bind_lines`' leading-empty count comes from `plan.header_rows()`, paired with the origin it must match. Routed through the one plan: the query caret's centre, `over_overlay_query`'s pointer band, `overlay_lens_at`'s clickable strip band, the active-facet mark's centre, the secondary column's upload origin, and `overlay_pane_fills`' split gap.
- **THE LIVE DEFECT IT FOUND, of the family's own class.** `over_overlay_query` tested the bare row pitch, `text_top .. text_top + lh`. On the FLAT family the beat inflates the QUERY line itself, so the field's box is `lh + header_gap` tall and cosmic-text half-leads its ink LOW inside it. Measured on the shipping default at 1200x800: the field draws `[64.0, 133.2]` with its caret centred at 98.6 and its shaped baseline at 106.0, while the pointer band ended at 91.2 — the I-beam appeared in empty air ABOVE the query text and the text itself took the plain arrow, missing by 7.4px at 1x and 14.8px at 2x. The GROUPED family was right by accident (its beat inflates the lens STRIP instead, leaving the query line a plain `lh`), which is how a parallel calculation survives review: it agrees on the arm somebody looked at. The cursor icon is the ONLY output that changed — 840 PNG probes and 840 sidecars over every world x three canvas/DPI cells x fourteen surfaces are byte-identical, measured by a since-retired capture sheet.
- **ITEM 219 — WHERE THE BEAT STANDS, and the blank band the fold opened.** The beat was folded into the LAST header line's box on BOTH families. cosmic-text CENTRES a line's glyph run in its box (`buffer.rs`'s `centering_offset = (line_height - glyph_height) / 2`), so on the FLAT family — whose one header line IS the query field — the field's own glyphs were drawn `header_gap / 2` below the bar's own top pad: measured on the shipping default at 1200x800, the query ink centred at 98.0 where its line box centres at 77.6, a 20.4px blank strip at the top of every takeover picker on every world. Reported against Mopoke/Currawong/Gumtree/Bilby/Bowerbird; present, byte for byte identically, on all twenty. **The rule is now one sentence: THE QUERY FIELD'S BOX IS ALWAYS EXACTLY ONE LINE.** `plan::beat_stands_alone` is the one owner of whether the beat rides the last header line's glyph metrics (a GROUPED card's lens strip, where the half-leading is exactly what seats the strip below the split seam) or closes the band as its own GLYPH-FREE LINE (a flat card, where there is nothing to seat). The shaper emits that line as one space at `OverlayRowPlan::beat_line()`'s height — DERIVED from the planned boxes, so a spacer the band did not plan is unreachable — and `OverlayGeom::shaped_first_row_line` is the one owner of the buffer-line index it shifts (a reader that re-derived `header_rows` measures the spacer as a candidate row). `split_bounds` collapsed from two arms to one: **the seam hangs from the QUERY FIELD's own bottom edge** plus `BREATHE_FRAC`, which is byte-identical arithmetic on the grouped family (the strip's top IS the field's bottom) and is what closes the flat card's bar around its own text. `first_top`, the candidate band, the selected row, keyboard nav and the card box are all untouched. Laws: `render/plan/tests.rs`'s `the_query_field_box_is_one_row_pitch_on_every_family` and `the_split_gap_is_carved_out_of_the_beat_below_the_query_field`, `render/tests/overlay_header_band_law.rs`'s `the_query_bar_closes_below_the_field_and_the_folded_beat_would_overrun_it`, and the real-pixel `render/tests/query_field.rs`'s `a_flat_pickers_query_ink_centres_on_its_own_line_in_every_world` — a DIFFERENTIAL oracle (the same card shot with and without query text, so ground, texture, placard and dither cancel), roster x two canvases x 1x/2x. Item 174's own non-vacuity law `the_pre_plan_query_band_genuinely_missed_the_field` was DELETED rather than shipped vacuous: the formula it reconstructed (`text_top .. text_top + lh`) is now the correct one on both families, so it could no longer fail on anything. Its user-visible outcome — the I-beam appears where the query text is — is still held, by the headline `the_drawn_query_field_the_pointer_band_and_the_caret_are_one_planned_box`.
- **ITEM 225 — A WORKSPACE'S `Bars` FOOTER PLATE ENDS WITH ITS FOOTER.** The plate ran to the card's bottom edge, which is right for a card that HUGS its content (the plate closes the card, and the two are the same line) and wrong for a summoned WORKSPACE, whose card comes from the CANVAS: the same rule painted a slab as tall as whatever vertical space the rows did not use, hanging below the footer's glyphs with nothing in it. On Cassowary, whose plate ink is `base_100` at `#050506`, that is the reported "oversized black sub-settings bar"; the same slab is on the other two `Bars` worlds in a paler ink. The workspace arm now takes the FOOTER'S OWN BAND — the row pitch LESS `overlay_footer_reclaim`, the one owner of how much shorter a footer line is than a row, which the card height already reads — and the contextual arm is untouched and byte-identical. Law: `render/tests/workspace_footer_plate.rs`'s `a_workspace_footer_plate_ends_with_its_footer_on_every_bare_plate_world`, three arms (the emitted quads: no workspace plate may be taller than one row of its own list; the pixels: the band the retired rule painted must read as workspace ground; and the exclusion, below), the retired rule written out inline for non-vacuity, x 1x/2x.
- **ITEM 236 — THE BARE-PLATE ROSTER IS NOT THE PLATE-DRAWING ROSTER.** `list_backing == BarePlates` is a claim about the CARD — no panel, no shadow, no border, so the rows sit bare on the canvas — and says nothing about what backs a ROW. Two of its five members, Mangrove and Magpie, are `ListStyle::Diagonal`: bare in exactly that sense and drawing no plate anywhere, their selection being a bright spine segment and a connector. Item 225's law and item 174's `content_rows` law both swept `BarePlates` while reasoning about plates, and the test-only `overlay_bar_rects_probe` SYNTHESIZED rects for the two diagonal worlds by calling `overlay_bar_selection` at dials (`6.0/10.0/24.0/HugLabel/All`) that no world authors and no frame draws — so both laws graded an invention on those cells, including the `!plates.is_empty()` non-vacuity guard. `ListStyle::draws_row_plates()` is now the one owner of the question, `overlay_selection_rects` is the one place a list style becomes row surfaces (production and probe both route through it), and **`overlay_bar_rects_probe` REFUSES on a style that draws no plates** — the misuse is a panic at the ask rather than a shape to be found later. Both laws gained a third arm that EARNS the exclusion by measurement: on each plateless bare-plate world the frame must emit no row surface at all (`overlay_row_surfaces_probe`), so a world that starts drawing plates fails there instead of quietly dodging the sweep.
- **ITEM 308 — A `Bars` FOOTER PLATE GETS THE NOTICE CHANNEL'S OWN RIM.** Cassowary's footer plate (`overlay_bar_unselected()` = `base_200`, on a page rooted at `base_100`) measured ΔE 1.91 from its own page — under the ≈2.3 JND, and invisible to the old absolute-luma gate because Firetail aborted the run first (item 306). `footer_plate_rim` (`render.rs`) is a new `SelectionPipeline`, drawn under `overlay_bars` from the SAME rect the footer plate itself uses (`OverlaySelectionRects::footer_plate`), grown one device px on every side — the identical mechanism `notice_rim`/`notice_plate` already use, coloured `theme::overlay_footer_plate_rim()` (`muted`, resolved fresh every frame, no `sync_theme_colors` entry — same reasoning as the notice channel). Re-measured with the rim: Cassowary 54.13/58.47 (1×/2×), Galah 22.33/28.08, Firetail 40.91/44.00 — all clear `render::tests::notice::PLATE_PRESENCE_MIN` (ΔE 15, made `pub(super)` and reused rather than re-derived: both channels earn presence the identical way, a value-stepped fill plus a one-pixel rim). Law: `render/tests/overlay_plan_law.rs`'s `footer_plate_clears_the_notice_channels_presence_floor_on_every_bars_world`, over the plate-drawing roster × both DPI tiers, the page read back from the same rect with the overlay closed (`notice.rs`'s own "what was actually there" technique) rather than a nominal token value.
- **ITEM 316 — A LOCATION ROW THAT PLANS NO GLYPH GETS NO PLATE.** Exposed, not introduced, by item 297: `PlanLine::Location`'s inline text is glyph-free wherever `LocationStyle::draws_inline()` is false (Cassowary's `RotatedRail`, composed off-card into the room's margin), but `overlay_unselected_bar_rects`'s theme-strip loop backed EVERY `item.is_none()` row (header or location) with a plate regardless — a visibly empty chip once the row's own text left. The loop now reads the same `draws_inline()` gate the shaper itself reads before pushing a location row's plate — never a named-world check, so a future non-inline style loses its chip for free and a future inline one keeps it. Law: `render/tests/overlay_location_plate.rs`'s `a_glyph_free_location_row_draws_no_plate_and_an_inline_one_still_does`, over the plate-drawing roster × every faceting `OverlayKind` × both DPI tiers — the one production row-surface probe (`overlay_row_surfaces_probe`) must emit nothing over the location row's own Y-slot on the excluded case and something there on an included one (non-vacuity), plus a real-pixel ground check on the excluded case.
- **THE WORKSPACE HEADER DOES NOT BUILD A ROW PLAN ON THE DOCUMENT HOT PATH.** `workspace_header_band` (`render/chrome/comparison.rs`) delegates its height to the pure `plan::header_band_height` seam. `comparison_viewport` reaches it from the relocated document owners (`column_left`/`column_width`/`doc_top`/`doc_clip_band`), so a full row plan there would multiply work across dozens of calls per frame. The shared height function is the correct planning boundary: one arithmetic owner, no retained plan, and no change to the O(visible) budget.
- **THE COMPLETE PER-FRAME GEOMETRY CENSUS DRAWS THE PLANNING BOUNDARY.** Device-free planning owns overlay header/candidate/accessory geometry, the search panel report, corner labels, ordinary HUD and streak cards, which-key, contextual popover placement plus hit spans, the spell card anchor, the gutter bottom stack, outline block/row slots, workspace split/staged regions plus the comparison viewport, and the caret-preview panel. These plans consume resolved canvas, row, padding, anchor and measured-text extents; they retain no tree and allocate only for visible rows. Text shaping and raster ink measurement remain with glyphon-facing chrome. Document visual rows, glyph advances, markdown ornament bounds, image boxes and table grids remain with `row_geom` and their existing caches because their inputs are shaped glyphs, decoded media or table measurements; copying them into a device-free plan would be a duplicate CPU renderer or an O(document) frame plan. Outline heading selection/elision, gutter label fitting, the rotated rail, placard/stipple masks, preview-caret shaped x/baseline and panel case spans likewise remain with their content or measurement owners, while their post-fit pixel placement is planned. The already-one-owner `OverlayGeom` adapters (`overlay_card_box`, ordinary/theme/workspace geometry) and the menubar and diagonal/bar visual layouts remain specialised state adapters: they translate feature-specific state directly into their single draw family rather than serving independent draw/hit/report consumers, so moving them would rename an owner without merging a rule. GPU pipelines, texture allocation, colour resolution, clip/upload, float/bar/notice dressing, frost expansion and draw ordering are execution state, not geometry planning.
- Law probes that report the plan for a law to compare against live in `render/tests/overlay_probe.rs`, not beside the draw code: a probe naming the logical selected row is not a render path, and keeping it out of `render/chrome` keeps item 164's sweep strict rather than growing an exception.
- **THE HEIGHT CLAMP (item 181, extended by item 184), `plan::fit_item_rows`.** The GROUPED family (`theme_overlay_geometry`) already divided its own `avail_px` by the row pitch to bound its item window; the FLAT family (`overlay_geometry`) capped its window only at a per-kind row COUNT (`OverlayKind::window_rows`) that knows nothing about the canvas. A flat picker whose count is its whole corpus — the theme picker, `window_rows() == theme::THEMES.len()`, once its runtime lens strip retired (making it flat, see below) — drew a card taller than the canvas at its own default size (`card_h: 934` against `canvas_h: 800`). `fit_item_rows(avail_px, lh, overhead_rows, min_items)` is now the one owner of "how many item rows fit"; `render/chrome/overlay_clamp.rs`'s `overlay_item_cap`/`overlay_flat_window` route the flat family AND the spell popup through it, `theme_overlay_geometry` routes the grouped family through the same `fit_item_rows`, so no consumer computes its own floor-division. Byte-identical wherever a picker's per-kind cap was already the binding constraint (every shipped flat/grouped picker at ordinary zoom/DPI). **ITEM 184 closed the residual item 181 left open:** a GROUPED picker deliberately cycled onto a sectioned lens carries extra fixed header overhead (the lens strip + real section headers), and at the documented zoom ceiling (3.0) combined with a short canvas that overhead ALONE — before a single item is counted — could still exceed the canvas even with the item-row floor forced to 1 (`card_h: 535.4` against `canvas_h: 460`, the command palette on its File lens; confirmed present on unmodified pre-184 code via `git stash`). `fit_item_rows` gained a `min_items` parameter: the FLAT family and the spell popup keep `min_items: 1` ("a card always attempts to show its own selection", byte-identical to item 181), while the GROUPED family now passes `min_items: 0` — when its own fixed chrome overhead alone cannot fit, the card answers with an EMPTY candidate band rather than a forced row that overruns the canvas. The lens strip, the section headers, AND the footer (`overlay_footer_lines`, the one owner both families now read for `keybindings_tips`, previously grouped-only-omitted and always empty in practice since only the flat Keybindings kind ever populates it) all count against `avail_px`. A no-op everywhere the floor did not already bind (`saturating_sub` alone clears the new floor whenever `fit_lines > overhead_rows`) — proven, not merely asserted, by `already_fitting_grouped_pickers_stay_byte_identical_across_the_floor_fix`, which fingerprints five ordinary grouped scenarios against numbers measured on the unmodified pre-184 code. Laws: `render/plan/tests.rs`'s pure `fit_item_rows_*` tests (the ordinary case, each family's own floor, the zero-pitch guard, non-vacuity against the reported theme-picker shape) and `render/tests/overlay_height_clamp_law.rs`'s device-level sweep (every `OverlayKind`, both list styles, four canvases at 1x/2x DPI with the LOGICAL window always at/above the app's own enforced minimum, plus a zoom sweep 0.5–3.0 against the theme picker, the command palette's "All" home, AND its sectioned lens) — three oracles per cell (the sidecar's `card_h`/`canvas_h`, the planner's own last-row bottom edge from a DIFFERENT function than `card_h`, and real pixel ink at the last row's baseline), a named regression pin reproducing the exact reported numbers for both items, and a non-vacuity floor proving the grouped family's empty-band path is genuinely exercised.
