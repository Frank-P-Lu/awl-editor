# awl docs — Render: adaptive column, theme caps, overlay chrome, picker rows

> Read before touching `render/`, `theme/model.rs` (RenderCaps), `overlay/`, `settings.rs` palette rows, or picker/row layout.

## Adaptive-column placement (`render/geometry.rs`)

- On a small screen the symmetric centered column cramped the margin outline while the right margin sat empty. `TextPipeline::column_left` is the one owner of an adaptive policy (no config knob): shifts right under pressure to grant the outline a rail (taking the empty right-margin space), back to symmetric when there's room. Every downstream reader (caret/selection/washes, hit-test, drag handle, gutter) composes it for free.
- Pure policy `adaptive_column_left`, one formula `desired_left.min(max_left).max(symmetric_left)`, three regimes (wide = byte-identical passthrough to the old column; narrow = shift, width never touched; narrowest = re-centers → outline auto-hides at its existing floor). Hide threshold + shift threshold read the same `left` (can't drift). Transition is instant (glide banked). **Live-only:** the feel of a real small-screen resize.
- **THE CONTENT CLIP — `TextPipeline::content_clip` / `clip_rects_to_band` (`render/rects.rs`).** The ONE resolved region every document-content, selection-adjacent quad must paint inside: horizontally the writing column ALWAYS (`column_left()`..`+column_width()`), vertically the whole canvas on an ordinary frame narrowed to whatever region the document layer is actually drawing in (`doc_clip_band`). A drag whose hit-test clamps to the page's own left edge, or a relocated comparison scrolled so a selected/composing/caret row leaves the region, both resolve through this one rect — bounding PAINT only, never the SELECTABLE range. `range_rects` (feeding both `selection_rects` and `search_match_rects`), `preedit_rects`, and the caret's own park gate in `prepare_caret_layer` all route through it; on an ordinary frame this is a no-op (`doc_clip_band` is `None`, and selection/caret x is already inside the column by construction). The vertical bound used to come from the diff-as-preview panel's card rect — the single case where a document ever drew somewhere other than the whole canvas. A real relocated viewport (`comparison_viewport`, below) now supplies `doc_clip_band` as its vertical extent; the emitters, the one owner and the by-name sweep are untouched, and the X arm is genuinely exercised because the region moves horizontally too. Laws: `render/tests/selection_clip_law.rs` (a no-wildcard, by-name check that each emitter's own body calls the shared owner, plus the runtime proof the relocated case actually clips — its straddling canvas is now DERIVED from row geometry, not from the clip's own output, so a reverted clip fails on an escaping rect instead of on a fixture that stopped qualifying).
- **Decorative-overhang emitters get their OWN Y-only clip, `clip_decorative_rects_to_band`, never `clip_rects_to_band`.** A follow-up audit found `fence_panel_rects` and `code_pill_rects` — pre-existing DECORATIVE quads whose whole point is to overhang the bare glyph column (`FENCE_PANEL_INSET_X`/`CODE_PILL_INSET_X`, "so the panel reads as a distinct surface rather than being clipped exactly to the glyph edges") — routed through the strict writing-column X-clip meant for selection-adjacent quads. Invisible with page mode ON (the page pad dwarfs both insets); UNIVERSAL with page mode off (`text_pad()` is hard-zeroed then, so `text_left() == column_left()` and there is no margin to absorb the inset): every fenced block's panel clipped flush on both edges every frame, and an inline-code pill lost its left cap whenever the span touched column 0 or the wrap edge. Two distinctly-named owners apply: `clip_rects_to_band` (X+Y, strict writing-column bound) stays SELECTION-ADJACENT-only (`range_rects`, `preedit_rects`; the caret gate reads `content_clip` directly); `clip_decorative_rects_to_band` (Y-only) is the DECORATIVE owner — `fence_panel_rects`, `code_pill_rects`, and the column-bound `wash_rects` comment/string/highlight buckets (structurally safe either way, kept on the decorative owner for one consistent story). Laws: `render/tests/washes.rs`'s `fence_panel_overhang_survives_content_clip_with_page_mode_off` / `code_pill_left_inset_survives_content_clip_at_line_start_with_page_mode_off` (each with a page-off zero-slack precondition, page mode off); the four `render/tests/selection_clip_law.rs` tests still hold unmodified — the selection/search/preedit/caret X-clip is untouched by this fix.

## The caret's cell geometry (`render/caret.rs`)

- **ONE CARET HEIGHT PER (FACE, ROW) ON A PROPORTIONAL WORLD, AND THE HISTORY IS THE REASON.** `caret_cell_vertical` OWNS the CELL caret's `(center_y, height)` at rest, and every cell-form caret reads it: the Block quad, Morph's fast-travel / ink-caret-world fold onto that quad (both via `caret_geometry`), Morph's support-body decision (`prepare_morph_body_or_empty`), and the glyphless SPACE BAR. On an ordinary Latin anchor, the row's TYPICAL-LETTER box (`caret_synthetic_ink_box` — the row's own real `max_ascent` × `facepitch::typical_letter_ratio`, the shipped face's measured MEAN of x-height and cap-height) grows by `CARET_INK_PAD` top and bottom, for EVERY Latin anchor — letter, ligature, space, end-of-line, empty row. A classified CJK anchor on a proportional world instead takes one stable IDEOGRAPHIC CELL from the face selected by the same document-language/script ladder that shaped its run: `facepitch::ideographic_cell_em` measures that bundled face's OS/2 typographic baseline split, normalises it to one em, and the shaped run supplies its font size. No kanji raster height enters the formula, so adjacent ideographs share one box while the full-square ink fits inside the authored pad. The resolved script faces are cached with the document attrs; the per-frame caret does no font-database walk. On a MONO world the existing row-scaled line cell (`caret_block_h`) and descender-aware bottom (`CARET_DESCENDER_PAD`) remain unchanged. The BAR forms (I-beam, Morph's line-start degrade) deliberately stay line-box (`ibeam_bar_dims`): an insertion bar marks a boundary between glyphs, so it has no glyph to hug.
- **BOTH DISCARDED SHAPES ARE WRONG, AND EACH WAS A FIX FOR THE OTHER — do not re-derive either.** A fixed fraction of the ROW is stable and hangs dead accent above a lowercase letter: measured on Gumtree/Literata at zoom 1, **8.63px above an `a`'s ink** while clearing an `l` by ~3px. Sizing to the ANCHORED GLYPH'S own raster box closes that to a letter-independent pad and makes the caret's top and bottom move with every letter typed — on the same face, per-glyph cells of 19.00px (`a`) to 26.00px (`l`) — which the user reported as distracting in ordinary prose and reversed by taste on 2026-08-12. The typical letter is the point between: 20.50px on that face, dead space above an `a` down to 4.50px (worst 5.60px anywhere in the roster at scale 1), and the earlier row cell was 22.40px. The caret therefore does NOT contain every letter's ink — an ascender rises a couple of px above it and a descender dips below the bottom pad. That is deliberate: a descender-aware bottom is a per-glyph rule, and one on the bottom edge is the same jump the top edge was relieved of. The mono arm keeps its own because its cell is row-derived and clears the band anyway.
- **THE RASTER READ STILL OWNS THE HORIZONTAL.** `TextPipeline::caret_anchor_raster_box` remains the single swash read on the caret path and returns the FULL placement box (`InkBox { left, top, width, height }`, plus the derived `descent()`); `caret_anchor_ink_box` layers the policy gate on it (no box on a MONO face, on a multi-char LIGATURE cluster, or on a glyphless / zero-mask anchor). The kerned-glyph horizontal fix and the mono descender extension ride it; nothing vertical on a proportional world does. Both ink corrections (x-shift and vertical re-centring) are scaled by the settle factor, so a moving caret is untouched, and the descender extension lives at the rest ENDPOINT rather than at the draw site (`layers.rs` holds no caret vertical geometry of its own — there is a grep-law) so the travelling streak has exactly one thickness rule.
- The two after-text glyph-mask roles keep distinct weights. Ordinary Morph uses `CARET_MORPH_DILATE_PX` (2.0 logical px) to make the accent silhouette deliberately bolder than its source letter. A `CaretBlockStyle::Filled` world (Cassowary's CRT phosphor cursor) uses `CARET_FILLED_KNOCKOUT_DILATE_PX` (zero): the block is already the affordance, so the covered glyph is knocked through at its true raster weight, including its own anti-aliasing, rather than emboldened a second time. `CARET_INK_PAD` (3.0 logical px) remains the small letter-independent margin around the cell form; it no longer derives its contract from Morph's unrelated expansion.
- **THE PROPORTIONAL FALLBACK READS `doc_family()`, NEVER `shaped_font` (found auditing item 105's own fix, before it shipped).** `sync_theme_colors` (the theme-picker's per-arrow preview step) switches the ACTIVE theme and re-tints every baked colour INSTANTLY but deliberately leaves `shaped_font` (the face the document is ACTUALLY shaped in) stale until the separately-DEFERRED `sync_theme_font` reshape catches up — the whole point of the split (docs/fonts.md's "Theme-preview debounce"). This matters because the caret's box is FONT-AWARE: reading the LAGGING `shaped_font` and left the caret itself showing the SOURCE world's geometry for the whole window between a preview's color retint and its reshape — exactly the surface `theme_preview_retint_regrounds_the_page_surface_on_every_world` (`render/tests/distinguishability.rs`) exists to guard, and it caught this directly (a full-frame pixel diff, Tawny→Magpie, 253px differing) before the fix shipped. The repair: the arm-selection GATE keys on `TextPipeline::doc_family()` (the LIVE effective face the active theme wants for this buffer kind — reads `theme::active()` directly, no lag) instead of `shaped_font` — correct because that gate decides between two structurally DIFFERENT formulas (line-cell vs ink-box), and drawing the wrong KIND of cell for a whole preview window is the coarser, more jarring failure. Law: `render/tests/caret_transition.rs`'s `caret_fallback_geometry_tracks_the_live_theme_not_the_lagging_shaped_font` — the fast unit-level companion to the pixel law, pinned at the exact seam, non-vacuous against a `shaped_font`-keyed reversion (its one fixture is an EMPTY buffer, where this distinction cannot yet show — see the next bullet).
- **THE WRAP-BOUNDARY TRAP — caret transition claims are measured ROW-RELATIVELY, never absolute (adjudicated 2026-07-26).** A run of spaces long enough to fill an entire wrapped visual row by itself — flanked above and below by real-ink rows of the SAME logical line — gives `caret_cell_vertical` a row whose typical-letter box is anchored to THAT row's own baseline — a genuinely different baseline from the row above or below it. Two independent audit passes measured the caret's ABSOLUTE pixel position stepping across that row's wrap boundary and reported a ~30px jump as a HIGH-severity defect; it wasn't one. Crossing a soft wrap moves the caret down exactly one row's `line_height` and back toward the left margin — correct, INTENDED behaviour — and an absolute-position delta cannot distinguish that row-pitch component from a genuine cell-geometry discontinuity, because it compares two rows that are never drawn at the same y in the first place. Isolating the two (subtract each column's own `caret_baseline_y()` before diffing) showed the ~30px figure was ~84% pure row pitch (a flat 32.00px on every proportional world, exactly this fixture's `line_height`); the genuine row-relative residual was 5.85px worst-case (Bilby) then and is 0.00px now that every anchor on a row shares one cell. Any future caret-transition claim across a wrap must diff row-relatively (this column's `cy` minus its OWN row's baseline), not the raw absolute `cy`, or it will re-derive this same false positive. Law: `render/tests/caret_transition.rs`'s `glyphless_row_transition_is_bounded_row_relatively_across_a_wrap` — sweeps every adjacent column pair of the reported fixture over the full proportional roster, asserting BOTH that the absolute delta is genuinely large (proving the fixture reproduces the reported jump) AND that the row-relative residual at the same seam stays bounded.
- Laws: `render/tests/caret_ink_box.rs` — the one-height claim across ascender / x-height / capital / descender with the formula RE-DERIVED from the face's own ratio, the roster × both-DPIs sweep of one caret top per row, the no-wildcard `CaretMode::ALL` form sweep, the mono uniform-grid law, the moving-streak law, the glyphless space / EOL / line-start-bar cases, the pad-vs-dilation bound, and the `layers.rs` grep-law; `render/tests/caret_transition.rs` — every adjacent-column seam (glyph→glyph, glyph→glyphless, runs, wraps, EOL, empty line, the ordered cross-product of a no-wildcard 10-class roster) asserted EQUAL rather than bounded; `render/tests/caret_one_height_pixels.rs` — the same claim measured off rendered PNGs at both DPIs, with a presence floor so "one height" cannot be satisfied by a caret that stopped drawing. **Every equality law carries the same non-vacuity oracle: the anchors' own raster ink must still be spread by several px, or uniformity is a fact about the fixture rather than about the caret.**

## Theme capabilities as data (`theme/model.rs::RenderCaps`)

- Render call sites never branch on world identity — they read authored `RenderCaps` expressions. `selection_style` and `caret_block_style` may each choose an independent `TwoColour` palette-role pair; one shared subtractive renderer swaps any pair, so black/white is not baked into the path. No-variation facts do not occupy theme data: overlay motion defaults to `MotionJuice::CALM`, Pane defaults to `PaneSplit::Split`, lava frost reads the shared `crate::lava` recipe, and `selection_ui` always derives from the surface ramp. Test-only overrides retain the dormant motion and Pane axes for mutation laws. The roster census reports every zero/single-adopter field by name and rejects any new unclassified field. Sparse authored expressions — Ruled, Diagonal directions, chamfer, ambient stars, icon-ground presets and background kinds — remain data. **No theme may need its own code path.**

Read by the ONE corner-mask owner (`render::chrome::TextPipeline::card_shape_texture`, called from `prepare_panel_card_elevation`, `overlay_draw_card`'s spell-popup arm, and `overlay_material.rs`'s scanline/placard materials — every console layer that draws a card-shaped quad resolves ITS OWN rect through this same function rather than deciding its corner independently): a plain `sd_round_rect` SDF (`shaders/selection.wgsl`) gets replaced by `sd_card_rect`'s CSG intersection with a diagonal half-plane, picked PER-HALF by the fragment's own `p.y` sign (`chamfer_top` above the card's own center, `chamfer_bottom` below), shared by the fill/border/shadow trio so the eight-edge boundary agrees across all three; the texture composites only over the FILL, sampled at the ABSOLUTE canvas pixel (not instance-local) so a Split Pane's two surfaces share one continuous phase across the open gap — Quokka's dot lattice with a pure horizontal rolloff (`halftone_rolloff`) keeping the left content column clear. The texture's own ink is DERIVED (`theme::card_texture_ink`, a `muted`→`base_300` blend) — never a raw/amber literal in the cap. `render::chrome::narrowed_chamfer_px` caps EACH half's chamfer at 40% of a card's own smaller dimension so a genuinely tiny surface (the spell popup) never lets the cut steal text room, while an ordinary short query bar stays untouched. The round's real fix was less the new axis than the OWNERSHIP: `overlay_material.rs` used to hardcode the placard's chamfer to `0.0` regardless of the card's real shape (a per-layer opinion independent of the card it bleeds against, the square-artifact bug's actual cause) — it now resolves through `card_shape_texture` against its OWN rect like every other layer, and `SelectionPipeline::chamfer()` (test-only) lets a law assert every layer agrees with the owner instead of trusting the call sites by convention.
- **ITEM 86's ZIGZAG margin ground, TILED INTO A FIELD BY ITEM 89** (`theme::Background::Zigzag{from,to,dir,tint,period_px,amplitude_px,angle,density}`, shader id 7) — a tiled field of repeating chevron ("V") rows over the gradient, in the SAME whisper-mark family as `Dots`/`Pinstripe` (composites through the shared `pattern_coverage` → `fs_main` mix pipeline, unlike `Bands`/`Waves`' own final-color branch). Quokka's old dot grid and Gumtree's old grass-`Bands` field BOTH moved here, each with its OWN authored dials so the two never read as a recolor of one asset: `period_px` is the TOOTH-WAVELENGTH dial (Quokka 100px, tight; Gumtree 170px, broad), `amplitude_px` the PROFILE dial (Quokka 24px; Gumtree 60px — and, through item 89's abutment rule, the field's ROW PITCH and the stroke's own thickness), `angle` the DIRECTION dial (Quokka ~54° steep diagonal; Gumtree ~15° near-horizontal), `density` the CONTRAST dial stacked on the shared `PATTERN_MAX_COVERAGE` ceiling (Quokka 0.60, bold; Gumtree 0.20, quiet). One shader function (`pattern_coverage`'s `shader == 7u` branch) reads all four via the SAME `params` vec4 slots Dots/Stripes/Bands already reuse per-shader (`params.x`=period, `.y`=angle, `.z`=amplitude, `.w`=density) — no new uniform layout, no per-world code path. `Background::Bands` is now DORMANT reusable infrastructure (Gumtree was its one assignee) — the exact "ships with zero worlds until one wants it" shape `edge: true` Dots already held. Laws: `render/tests/backgrounds_item86.rs` (the round's DESIGN brief — roster, four-dial distinctness, real-pixel contrast), `theme::tests`' data-level roster + palette laws. **ITEM 89 — the FIELD fix (correctness, not a new taste round), in TWO parts.** *(a) The FOLD.* The `shader == 7u` branch computed `center` from the ALONG-travel coordinate alone and took `abs(ry - center)`, which is ONE continuous chevron curve embedded in the plane: teeth repeated along travel, nothing repeated the curve ACROSS it, so a margin carried a single wandering stroke with large blank areas (62% of a tall Gumtree margin, the right two thirds of a Quokka one, measured at literally zero ink) and a taller window gained no second row — it only let the same stroke travel further off-canvas. The fix FOLDS the across-travel coordinate through a row pitch (`d = |fract((ry - center)/row_h + 0.5) - 0.5| * row_h`), turning the single curve into the family `center + k*row_h` — a genuinely tiled field. *(b) The ABUTMENT RULE — the coverage repair.* The fold's first cut set `row_h = period_px` (a square lattice). That TILES but does not COVER: row `k`'s ribbon only ever visits `ry` in `[k*row_h - amp - t, k*row_h + amp + t]`, so whenever `2*amp + 2*t < period_px` the field carries a hard BLANK LANE of `period_px - 2*amp - 2*t` that no chevron enters at any point of the plane — ~70px every 250px on the dials that first shipped, and at ordinary-but-shorter windows a narrow margin could sit wholly inside one (verified at the app's real adaptive column geometry: an 80x182px band of a 1600x600 Gumtree right margin, and a 27x234px cell of a 1400x700 left margin, at exactly zero deviation; Quokka's finer field was clean at every size). `row_h` is now `2.0*amp + thickness` (`theme::Background::zigzag_row_pitch_px` is the host mirror), so each row's ribbon sweeps exactly its own lane and its CORE sweeps a lane plus `0.2*t` of overlap: rows ABUT for ANY dials at any angle — coverage stopped being a property of the dial pair and became a property of the shader. (**Item 100** corrected that claim's scope: it read "any viewport size or aspect" and that clause was false — a viewport is a ROTATED RECTANGLE of the plane, so it inherits the guarantee only while it holds a whole tooth of travel; a `period_px: 2000`/`amplitude_px: 150` field on a 1200x800 canvas leaves a measured 78px lane. Bounded by the TOOTH, which `ZIGZAG_MAX_ROW_PITCH_PX` does not bound; no shipping world is within 4x, and that ratio is now the authored guard.) The old amplitude-vs-period collision clamp retired with it (abutting rows cannot smear). `period_px` is now the TOOTH wavelength alone; `amplitude_px` carries the profile, the pitch and the thickness. Dials: Quokka 100px/24px UNCHANGED (its field already covered every margin cell at every swept viewport), Gumtree 170px/60px — the same ~0.35 profile ratio item 86 authored (85/250), the whole field scaled to a pitch a page margin can hold. Recorded cost: Gumtree reads ~6 broad rows down an ordinary window where the first cut read ~3, and that reading is NOT recoverable — a void-free chevron's teeth span its own pitch by construction, so "rows three times the height of their own teeth" and "no blank lane" are mutually exclusive; broadness now lives in the tooth wavelength, the 2.5x pitch ratio against Quokka, and the low density. The draw call is still the LITERAL `pass.draw(0..3, 0..1)` fullscreen triangle (a handful of added fragment ALU ops; zero CPU work, zero new uniforms). Laws: `render/tests/backgrounds_item89.rs` — a per-cell OCCUPANCY grid SWEPT over twelve `(window, measure)` shapes (heights 500..1600, aspect 0.56..2.37, including both verified failures) at the app's OWN `TextPipeline::column_left`/`column_width` owner and in BOTH placement regimes; **item 100 gave that headline law its teeth** — it had SURVIVED the exact regression it names (1.43x its floor against 5.48x healthy) because a 3x3 partition makes cells up to 116x266px, so the cell is now DERIVED from the field's own geometry (`P*|sin a|` by `P*|cos a|`, the smallest axis-aligned rect whose across-travel chord reaches a whole row pitch: Quokka 41x30, Gumtree 33x122) and the ink floor is a twentieth of the field's own structural areal density `2t/pitch` rather than a bare non-zero — 4712 cells graded, tightest occupancy 1.5x the floor, and 1595 cells at literally zero ink once the pitch rule is reverted. Also: a no-blank-LANE law scanned on the ACROSS-TRAVEL axis (a screen-`y` scan cannot see a lane once the angle is nonzero — the trap that hid this); an EVENNESS bound pinning the widest fully-blank horizontal band of any swept margin (174px as first shipped → 60px at real GPU pixels); the abutment THEOREM over 1600 arbitrary dial settings; an authored row-pitch bound (`theme::ZIGZAG_MAX_ROW_PITCH_PX`); a row-rhythm law; a height-scaling law; zero mark ink inside the writing column; byte-determinism at two canvas sizes; a WGSL structural tripwire on the fold AND the abutment rule; and a host mirror kept in lockstep with the GPU, carrying the first cut's pitch rule as a second arm purely so the laws can be proven capable of catching what it did. All pixel claims are DIFFERENTIAL (the world as authored minus the same world with `density: 0.0`, so gradient + dither + quantization cancel exactly and the measurement is the mark alone) — `mark_field` is that oracle's one owner, reused by item 86's contrast law.
- **ITEM 158's DECKLE margin ground** (`theme::Background::Deckle{ground,layer,deckle,weave,period_px,wander_px,density}`, shader id 9) — the handmade-paper MATERIAL field, and the roster's tenth ground. Quasi-random CONTOUR LANES, seeded per lane index and torn by a fixed two-tone sine wander, drawn only in the margins and computed entirely from the fragment position plus the page column. Static: no clock, no texture, no asset. ONE theme-owned dial, `theme::Weave`, picks the profile — `Strata` indexes the lanes on DISTANCE FROM THE PAGE COLUMN (so the contours gather around the writing page and MIRROR across it by construction; Paperbark's) and `Fibres` indexes them on screen `y` as thin strokes plus a diagonal vein family (reusable, DORMANT, the `Bands` / `Dots { edge: true }` shape — item 159 is its intended first assignee, and adopting it is one word in a world literal, not a renderer change). The scalar rides `params.w` through the new `BgDesc::weave` slot, whose INERT default is `0.0` for every ground with no weave (`Background::weave_mode` is the one owner); pitch/wander/density take `params.x/y/z`. `density == 0.0` collapses BOTH profiles to their flat ground EXACTLY — that is deliberate, and it is what gives the family item 86's `mark_field` differential oracle for free. Coverage is a property of the SHADER, not of a dial pair (item 89's abutment lesson): `deckle_rgb` CLAMPS the authored pitch to `DECKLE_MIN_PITCH_PX`, below which the deckled edge — a fraction of a lane — would fall under a pixel and alias. Laws: `render/tests/backgrounds_item158.rs`, whose swept axis is the MARGIN'S OWN WIDTH (the lanes are indexed on page distance, so how many a margin can show is a property of that margin, not the window), times 1x/2x DPI.
- **ITEM 186's GROUND COORDINATE SPACE — every authored ground quantity now declares whether it is COMPOSITION or SAMPLING.** Before it, `scale_px`, `period_px`, Dots' 24px cell and Deckle's pitch were all PHYSICAL pixels by accident of the coordinate a fragment shader runs in, so a 2x display rendered a ground at half its logical size and showed roughly twice as many elements — invisible to every law, because a capture is only ever internally consistent with itself. ## Rotated labels (`rotated_label/` + `shaders/rotated_label.wgsl`)

- **awl draws text at ONE angle unless a label asks otherwise.** glyphon 0.11 carries no transform anywhere — `TextArea` exposes `left/top/scale/bounds/default_color/custom_glyphs`, `CustomGlyph` exposes `left/top/width/height`, and there is no rotation, skew or matrix in the crate — so every run the document layer draws is upright and a world wanting a turned or slanted cue has no way to say so. `rotated_label` is that capability and only that: the caller shapes ONE short run into a `GlyphBuffer` (whichever face, size and colour its theme data names), `LabelMask::compose` composes that run's whole coverage into ONE R8 image on the CPU — the same swash cache glyphon rasterises from — and `RotatedLabelPipeline` paints it through ONE quad whose vertices are rotated onto a unit axis. The rotation is the axis rotation `shaders/caret.wgsl` already performs for the caret streak, applied to a glyph mask instead of a rounded rect; `SelectionPipeline::prepare_rotated` was the same step for selection quads.
- **It cannot become a second prose renderer.** The mask reads `layout_runs().next()` and stops, so there is no line breaking, no per-line alignment, no wrapping and no selection — a paragraph is structurally unreachable and the document layer stays the one prose renderer. The pipeline draws one label; a second is a second instance, not a longer buffer.
- **The frame is pure and separately owned** (`rotated_label/geometry.rs`): `label_axis_deg` (0° reads left to right, 90° bottom to top — screen pixels are y-down, so a reader's counter-clockwise turn is a negative one, and the four quadrant axes are returned EXACTLY rather than through the transcendentals, which is what makes a quarter turn a lossless texel transpose), `label_point`/`label_local` (the run's frame on and off the screen), `label_quad`, `label_bounds` (the TIGHT axis-aligned extent, for reserving a gutter or proving non-overlap) and `label_hit` (the rotated box, NOT the bounds, which at a slant over-claims its own corners). `unit_axis` is the one normaliser both the geometry and `prepare` route through, so the CPU's measurements and the GPU's quad cannot disagree; it degenerates to the shared inert `selection::UPRIGHT_AXIS` on a zero/NaN input.
- **Quality is MEASURED.** At 0/90/180/270° the transform is lossless: the composed coverage arrives with ink mass 1.0000, mean absolute error 0.0000 and full stroke/gap contrast, at 1× and 2×. At an arbitrary slant it is one bilinear resample and nothing more — the rendered canvas matches an ideal bilinear rigid rotation computed independently on the CPU to within 0.005 of full coverage, so the softening a slant costs is the unavoidable price of rotating a raster, not ink the pipeline loses. The composed mask carries a one-pixel transparent border because a rotated quad has no anti-aliasing of its own and would otherwise cut a stem square at its boundary. Laws: `rotated_label::tests` (the frame, oracled by polygon winding and measured side lengths) and `render/tests/rotated_label_item235.rs` (the pixels, oracled by the CPU-composed coverage image, which no rotation code touches).
- A per-instance colour PAIR interpolates along the run's own baseline, so a world whose visual language is a gradient line gets one without a second code path; equal values are a flat label. Nothing here reads a theme — which string, which axis, which colours, where, is theme data a caller supplies.
- **Two world expressions share ONE preparation owner** (`render/rotated_location.rs`'s `TextPipeline::prepare_rotated_location_label`, dispatched by `render/chrome/rotated_location.rs` on `theme::LocationStyle`): Cassowary's `RotatedRail` (90°, composed against the ROOM — see the paragraph below) and Magpie's `Raked` (item 224 — the location cue stays in item 220's own inline slot, unmoved, but reads along the diagonal spine's own rake instead of upright). Both variants carry a `LocationLabelStyle`: face (`Body` / `Mono` / `Chrome`), expression-relative scale, palette-role ink (`Flat` / `Gradient`), real shaper tracking in em, and locator grammar (`Label` / truthful indexed locator). Only placement and overflow remain expression mechanics — one `RotatedLabelPlacement`, decided in the dispatcher; text formatting, mask compose, cache, and fit solver are shared verbatim. Magpie authors its former chrome-face / 0.92 / muted→base-content / untracked label values as data, so its pixels stay unchanged. Its angle is DERIVED, never pinned: `render/chrome/diagonal.rs::location_axis_deg` reads the diagonal composition's own `ROW_STEP`/row-height ratio — and specifically the row's own MEASURED step (`DiagonalClusterRail::spine_step`, which a too-narrow card's `TRAVEL_MAX_BAND_FRACTION` yield can shrink below the authored constant), so the cue and the spine beside it cannot drift apart even under that yield. At Magpie's own near-vertical, non-quadrant angle the round trip measures contrast 0.65 at 1× and 0.83 at 2×, with worst-case departure from an ideal bilinear rigid rotation of 0.0046 of full coverage — the softening a slant costs, not ink the pipeline loses; supersampling was deliberately declined (it would buy at 1× what 2× already gives, at the cost of letterforms no longer matching their upright siblings). Laws: `render/tests/raked_location_item224.rs`.

- **`RotatedRail` is composed against the ROOM, not the card** (`render/chrome/rotated_location.rs`'s `rotated_rail_placement`). The cue takes the wordmark placard's own outer MARGIN and sits just ABOVE it, while its authored scale remains relative to the placard's own type size. ## The scene planner (`render/plan/`) — item 174

- **ONE deterministic, device-free layout stage between the measured inputs and the GPU.** It consumes the `ViewState` projection (the pipeline's `overlay_*` mirror), the already-resolved card box, the overlay row pitch and the grouped display-line sequence, and emits INSPECTABLE primitives plus INTERACTION geometry: one `PlannedRow { display, item, top, height }` per candidate DISPLAY LINE, `row_at(px, py)`, `display_at(py)`, `selected_display()`, `content_rows()`/`footer_top()`. It shapes nothing, measures nothing, reads no clock and touches no wgpu — so presentation decisions are assertable without a device (`render/plan/tests.rs`).
- **THE FORWARD `row -> y` ARITHMETIC AND ITS INVERSE ARE PRIVATE TO `plan/overlay_rows.rs`.** `overlay_row_top`, `overlay_row_of` and `overlay_row_index` are gone from `render/chrome`: a consumer cannot re-derive a row's position, only read it off the plan the pixels came from. Held by `render/tests/overlay_plan_law.rs`'s `only_the_planner_derives_an_overlay_row_position` — sentinels for the retired call names, `header_rows as f32`, AND for stepping off the band origin (`first_top` × a row count), which is the shape that hid `livingband::covered_rows`' own grid and the footer plate's seat for two years.

## Picker hover/click stability + movement latency (`app/input/mouse.rs`, `overlay/nav.rs`, `probe.rs`)

- **THE REAL-MOTION HOVER GATE.** A theme-picker world jump previews the destination world's rail/size/type/material immediately (reanchor, Pane↔Bars, a settling font reshape) — but that re-layout must never itself read as a pointer gesture. `OverlayState::hover_at(px, py, hit)` is the ONE door `app/input/mouse.rs::overlay_hover` calls on every `CursorMoved` (real travel or a platform-synthesized duplicate at the identical coordinates): it compares `(px, py)` against `OverlayState::last_hover_px` and only re-hit-tests/re-selects (`hover_select`) when the pointer's own PHYSICAL position genuinely changed since the last check — a hit-test RESULT changing on its own, with the pixel unmoved, is a no-op. Pure and GPU-free (`hit` is a caller-supplied `Option<usize>`, not a pipeline call), so it's unit-tested directly. Laws: `overlay::tests::hover_at_gates_on_real_pointer_motion_not_a_relayout_hit_test_change` (proves BOTH that the hazard is real — an ungated `hover_select` really does cascade — and that the gate refuses it), `overlay::tests::hover_at_off_a_row_records_position_without_selecting`, `render::tests::overlay_hover_stability_law` (the same hazard against real pipeline geometry: a deliberate Wagtail→Cassowary rail crossing moves what a stationary pixel hits). - **THE MOVEMENT-SLOP WIDENING + KEYBOARD BASELINE.** The exact-motion gate closed EXACT-pixel duplicates, but left a hazard the exact-equality check couldn't see: a list WINDOW SCROLLING under a genuinely resting pointer (a real keyboard `move_sel` deep enough to shift the candidate window) changes which row a stationary pixel hits, and any real `CursorMoved` past that point — even a single physical pixel of a resting hand's ordinary hardware jitter — used to steal the keyboard's own selection outright. `hover_at` now gates on SQUARED DISTANCE against `HOVER_MOVE_SLOP_PX` (private to `overlay::nav`, one owner; 4.0px, matching `app::DRAG_ARM_SLOP_PX`'s identical "content relocating under a stationary pointer" precedent) rather than bare inequality — real travel PAST the slop still takes over on the very first such event, no added latency, no dead zone; the anchor is STICKY below the slop (stamped forward only on a reported move) so a genuinely slow drag still crosses the threshold from its original anchor rather than re-basing itself every sub-slop increment. The OTHER half: `OverlayState::arm_hover_baseline(px, py)` re-anchors the gate to the pointer's CURRENT resting position, called by the shared keyboard-dispatch seam (`App::apply` live, `ReplaySession::apply_chord` headless) after every keyboard-driven action, AND by `App::overlay_wheel` — the mouse wheel drives `move_sel` exactly like ↑/↓ (a second "deliberate crossing" input class, same as the keyboard) but is dispatched straight from `on_mouse_wheel`, never through `apply`, so it stamps the baseline itself rather than relying on `apply`'s stamp — without either stamp, a session with no prior hover (`last_hover_px` still `None`) would let the pointer's first incidental `CursorMoved`, however small, read as unconditional motion under `hover_at`'s own cold-start rule and hand the selection to wherever a motionless hand happens to rest. `HOVER_MOVE_SLOP_PX` is now a re-export of `app::DRAG_ARM_SLOP_PX` itself (not a second `4.0` literal), so the two gates cannot drift apart under a future retune of either.
