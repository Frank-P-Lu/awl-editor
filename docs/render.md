# awl docs — Render: adaptive column, theme caps, overlay chrome, picker rows

> Read before touching `render/`, `theme/model.rs` (RenderCaps), `overlay/`, `settings.rs` palette rows, or picker/row layout. Moved verbatim out of CLAUDE.md 2026-07-22 (queue item 17); earlier round history: `git log -p CLAUDE.md`.

## Adaptive-column placement (`render/geometry.rs`)

- On a small screen the symmetric centered column cramped the margin outline while the right margin sat empty. `TextPipeline::column_left` is the one owner of an adaptive policy (no config knob): shifts right under pressure to grant the outline a rail (taking the empty right-margin space), back to symmetric when there's room. Every downstream reader (caret/selection/washes, hit-test, drag handle, gutter) composes it for free.
- Pure policy `adaptive_column_left`, one formula `desired_left.min(max_left).max(symmetric_left)`, three regimes (wide = byte-identical passthrough to the old column; narrow = shift, width never touched; narrowest = re-centers → outline auto-hides at its existing floor). Hide threshold + shift threshold read the same `left` (can't drift). Transition is instant (glide banked). **Live-only:** the feel of a real small-screen resize.
- **THE CONTENT CLIP (item 84) — `TextPipeline::content_clip` / `clip_rects_to_band` (`render/rects.rs`).** The ONE resolved region every document-content, selection-adjacent quad must paint inside: horizontally the writing column ALWAYS (`column_left()`..`+column_width()` — the SAME box the diff-preview card draws at, so "the writing column" and "the active card" are one region), vertically the whole canvas on an ordinary frame narrowed to the diff panel's own inset band while a preview is up (`doc_clip_band`). A drag whose hit-test clamps to the page's own left edge, or a diff transcript scrolled so a selected/composing/caret row leaves the card, both resolve through this one rect — bounding PAINT only, never the SELECTABLE range. `range_rects` (feeding both `selection_rects` and `search_match_rects`), `preedit_rects`, and the caret's own park gate in `prepare_caret_layer` all route through it; on an ordinary frame this is a no-op (selection/caret x is already inside the column by construction — only the diff-panel vertical case genuinely trips it). Laws: `render/tests/selection_clip_law.rs` (a no-wildcard, by-name check that each emitter's own body calls the shared owner, plus the runtime proof the diff-panel case actually clips).
- **ITEM 84-FIX — the decorative-overhang emitters get their OWN Y-only clip, `clip_decorative_rects_to_band`, never `clip_rects_to_band`.** A follow-up audit found item 84 had ALSO routed `fence_panel_rects` and `code_pill_rects` — pre-existing DECORATIVE quads whose whole point is to overhang the bare glyph column (`FENCE_PANEL_INSET_X`/`CODE_PILL_INSET_X`, "so the panel reads as a distinct surface rather than being clipped exactly to the glyph edges") — through the strict writing-column X-clip meant for selection-adjacent quads. Invisible with page mode ON (the page pad dwarfs both insets); UNIVERSAL with page mode off (`text_pad()` is hard-zeroed then, so `text_left() == column_left()` and there is no margin to absorb the inset): every fenced block's panel clipped flush on both edges every frame, and an inline-code pill lost its left cap whenever the span touched column 0 or the wrap edge. Fix: two distinctly-named owners — `clip_rects_to_band` (X+Y, item 84's strict writing-column bound) stays SELECTION-ADJACENT-only (`range_rects`, `preedit_rects`; the caret gate reads `content_clip` directly); `clip_decorative_rects_to_band` (Y-only, the fn's pre-84 body, restored verbatim) is the DECORATIVE owner — `fence_panel_rects`, `code_pill_rects`, and the column-bound `wash_rects` comment/string/highlight buckets (structurally safe either way, kept on the decorative owner for one consistent story). Laws: `render/tests/washes.rs`'s `fence_panel_overhang_survives_content_clip_with_page_mode_off` / `code_pill_left_inset_survives_content_clip_at_line_start_with_page_mode_off` (each with a page-off zero-slack precondition, page mode off); the four `render/tests/selection_clip_law.rs` tests still hold unmodified — the selection/search/preedit/caret X-clip is untouched by this fix.

## The caret's cell geometry (`render/caret.rs`)

- **THE INK BOX IS THE CARET'S ONE DESCRIPTION OF A LETTER (item 91).** `TextPipeline::caret_anchor_raster_box` is the single swash read on the caret path and returns the FULL placement box (`InkBox { left, top, width, height }`, plus the derived `descent()`); `caret_anchor_ink_box` layers the policy gate on it (no box on a MONO face, on a multi-char LIGATURE cluster, or on a glyphless / zero-mask anchor) and is the ONE funnel every ink-derived caret rule passes through. The horizontal half (the kerned-glyph fix) already rode it; item 91 added the vertical.
- **`caret_cell_vertical` OWNS the CELL caret's top and bottom** — `(center_y, height)` for the resting pose — and every cell-form caret reads it: the Block quad, Morph's fast-travel / ink-caret-world fold onto that quad (both via `caret_geometry`), and the glyphless SPACE BAR. The **ink box grown by `CARET_INK_PAD`** top and bottom on a proportional world, single-glyph anchor; the **row-scaled line cell** (`caret_block_h`) with the descender-aware bottom (`CARET_DESCENDER_PAD`) folded in, on a MONO world only. Descenders need no separate rule — `height - top` is already below the baseline in the same box. The BAR forms (I-beam, Morph's line-start degrade) deliberately stay line-box (`ibeam_bar_dims`): an insertion bar marks a boundary between glyphs, so it has no glyph to hug.
- **The bug it fixed was structural.** The bottom had a glyph-aware rule and the top did not, so the two edges could not agree: `CARET_BLOCK_H` is a fixed 0.8 fraction of the row centred on the line box, giving every letter the same top while the real ink top moves with the letter — measured on Gumtree/Literata at zoom 1, **8–9px of empty accent above `a`/`m`/`g`/`y`**, ~3px above `i`; after, a letter-independent 2–3px on all of them. The descender extension used to be re-derived at the draw site (`layers.rs::prepare_caret_block`) off the already motion-blended rect; folding it into the rest ENDPOINT is algebraically identical at settle 1 and lets `motion_geometry` blend it out mid-glide, so the travelling streak has exactly one thickness rule. Both ink corrections (x-shift and vertical re-centring) are scaled by the settle factor, so a moving caret is untouched.
- `CARET_INK_PAD` (3.0px at zoom 1) sits deliberately ABOVE `CARET_MORPH_DILATE_PX` (2.0): on a `CaretBlockStyle::Filled` world (Cassowary's CRT phosphor cursor) the block KNOCKS the glyph out with the morph silhouette dilated by that constant, so a pad at or below it would let the knockout eat the lit cell.
- **ITEM 105 — THE PROPORTIONAL FALLBACK JOINED THE SAME FORMULA.** Item 91's two arms each proved correct in isolation but never proved the TRANSITION between them: a proportional world's glyphless/ligature fallback centred on `caret.pos.y` (the row-box GEOMETRIC centre), while the ink-box arm one column over centres on the font BASELINE — two unrelated conventions with no reason to agree, and a user's paired release screenshots caught the resulting jump (`aaa`'s Block caret on the final `a` versus one column later at end-of-line — 2–13px at zoom 1 depending on world/glyph class, reproduced on 11/11 proportional worlds, 0/7 mono). The fix: on a PROPORTIONAL world only, the fallback now reads the SAME `baseline - top + height/2` / `height + 2·CARET_INK_PAD` formula as the ink-box arm, fed either a REAL raster box (a multi-char LIGATURE cluster — `caret_anchor_ink_box` gates it out of the ink arm only because one glyph's ink can't be fairly SPLIT across its chars horizontally, not because its vertical ink is untrustworthy) or, for a truly glyphless anchor, a SYNTHETIC typical-letter box (`TextPipeline::caret_synthetic_ink_box`): the row's own real `max_ascent` (from the SAME row lookup the baseline itself uses — `caret_row_metrics`, widened from `caret_baseline_y`) times the anchored family's own measured typical-letter/ascent ratio (`facepitch::typical_letter_ratio` — the MEAN of the face's x-height and cap-height ratios, read via skrifa off the shipped font bytes; the mean, not bare x-height, because a pure x-height reference reproduces item 91's bug in miniature against an ASCENDER neighbour). A MONO world is untouched — item 97's uniform grid never reads any ink box, real or synthetic, so there is no seam to jump across there (0/7 confirmed). `caret_row_metrics` also fixed a latent row-lookup gap it inherited from the original `caret_baseline_y`: the hand-rolled column→row predicate never matched the true END-OF-LINE column on an unwrapped line (`col < end_col` is never true there), silently falling to a crude `font_size * 0.8` ascent guess instead of the row's real `max_ascent` — invisible before item 105 (nothing read baseline/ascent at a glyphless anchor), but a ~30% systematic error once the synthetic box needed it. Reusing the canonical `pick_row_index_aff` (the SAME resolver `visual_row_top_aff`/`col_x_and_advance_aff` already ride) fixed it for free. Full closure is not achievable for every glyph class with one fixed synthetic reference — an ASCENDER, a DESCENDER, a LIGATURE, or a bare PUNCTUATION mark is legitimately taller/shorter than a "typical letter" (the ink-box arm's own letter-to-letter spread already shows a comparable gap with no bug involved, e.g. `l` vs `a` on Literata: 25px vs 19px); those classes are held to a wider, still-authored bound instead, and are proven never WORSE than the pre-105 formula on that same class.
- **THE PROPORTIONAL FALLBACK READS `doc_family()`, NEVER `shaped_font` (found auditing item 105's own fix, before it shipped).** `sync_theme_colors` (the theme-picker's per-arrow preview step) switches the ACTIVE theme and re-tints every baked colour INSTANTLY but deliberately leaves `shaped_font` (the face the document is ACTUALLY shaped in) stale until the separately-DEFERRED `sync_theme_font` reshape catches up — the whole point of the split (docs/fonts.md's "Theme-preview debounce"). Pre-105 this never mattered: a glyphless anchor's fallback was one constant formula regardless of font identity, so nothing color-only-visible read font identity at all. Item 105's font-aware fallback would have read the LAGGING `shaped_font` and left the caret itself showing the SOURCE world's geometry for the whole window between a preview's color retint and its reshape — exactly the surface `theme_preview_retint_regrounds_the_page_surface_on_every_world` (`render/tests/distinguishability.rs`) exists to guard, and it caught this directly (a full-frame pixel diff, Tawny→Magpie, 253px differing) before the fix shipped. The repair: the arm-selection GATE keys on `TextPipeline::doc_family()` (the LIVE effective face the active theme wants for this buffer kind — reads `theme::active()` directly, no lag) instead of `shaped_font` — correct because that gate decides between two structurally DIFFERENT formulas (line-cell vs ink-box), and drawing the wrong KIND of cell for a whole preview window is the coarser, more jarring failure. Law: `caret_transition_item105.rs`'s `caret_fallback_geometry_tracks_the_live_theme_not_the_lagging_shaped_font` — the fast unit-level companion to the pixel law, pinned at the exact seam, non-vacuous against a `shaped_font`-keyed reversion (its one fixture is an EMPTY buffer, where this distinction cannot yet show — see the next bullet).
- **THE REPAIR ROUND (2026-07-26, queue item 105 reopened — item 91's own fix did not fix the live bug).** The FIRST landing (above) synthesized its glyphless-anchor box from a per-font MEAN(x-height, cap-height) ratio — a single fixed reference that closed the reported x-height class (`aaa`→EOL) but was never swept against a CAPITAL letter, which landed WORSE than the pre-105 code on 11/11 proportional worlds (new Δ 2.3–4.4px vs old Δ 0.4–2.9px) — and the WIDE-bound "no worse than before" law meant to catch exactly that regression could not, because its ceiling floored at a flat 7.5px regardless of how small the old delta was. Two structural fixes: (1) `caret_cell_vertical`'s fallback arm now BORROWS the immediately PRECEDING column's own real `InkBox` (`raster_box_at`) when one exists, instead of synthesizing an approximation — a glyphless cell beside a real letter draws with THAT letter's exact ink, closing the adjacent seam to (near-)zero for every glyph class, not merely x-height, because it no longer guesses; the synthetic ratio survives only for a genuinely glyphless anchor with NO real neighbor (an empty line, or column 0). (2) `caret_synthetic_ink_box`'s ratio lookup now keys on `caret_row_metrics`'s own THIRD element — whichever font actually produced the paired `max_ascent` (`shaped_font` for a real shaped row, `doc_family()` only for the theme-independent empty-line approximation) — never an independently-chosen font: multiplying one font's ascent by a DIFFERENT font's ratio (the first landing's bug, invisible on the empty-buffer law since that branch never reads font identity) produced a measurable mixed-font pop on ordinary text during a theme-picker scrub (worst case 5.19px, Tawny→Bilby) that the repair halves (worst case 2.76px) without claiming full closure — the row's on-screen geometry genuinely IS still the source font's until the deferred reshape catches up, so some residual is inherent to the split, not a bug. Laws: `every_glyph_class_closes_exactly_at_the_literal_eol_seam` (every class, literal adjacency, exact closure) and `caret_synthetic_ratio_reads_the_same_font_as_its_paired_ascent` (the mixed-font lag, swept over every mono-source × proportional-destination pair) in `caret_transition_item105.rs`.
- **NEIGHBOR-BORROW, THREE ROUNDS (rounds 2–3, 2026-07-26).** Round 1's single-neighbor borrow (`raster_box_at(col - 1)`, above) closed the literal reported shape but left two shapes open: a glyphless anchor at COLUMN 0 (`" A"`, no `col - 1` to borrow at all) and a RUN of 2+ glyphless columns (`"A  "`, the second column's own `col - 1` is itself glyphless). **Round 2** (`nearest_row_raster_box`) searched OUTWARD from the anchor in both directions, bounded to the caret's own visual row, nearest distance wins (backward preferred on a tie) — closing both shapes, but a hard PICK borrows exactly ONE side's ink. A single glyphless column with a DIFFERENT real letter on EACH side (a table's `"| 1"` — pipe one side, digit the other, tied at distance 1) reads as pure pipe ink: the backward seam (pipe→space) closes to 0.00px while the untouched FORWARD seam (space→digit) inherits the WHOLE pipe-to-digit gap (measured 5–8px, three worlds over the file's absolute ceiling) — flipping the tiebreak to favour forward would only rotate the same whole gap onto the other seam, not fix it. The same hard pick showed a matching defect on a RUN of 4+ glyphless columns flanked by two different letters: the interior column where "nearest" switches sides is a hard, single-column STEP with nothing between to soften it (measured 6.5–7.0px on Bombora). **Round 3** makes the borrow NON-DIRECTIONAL: `nearest_row_raster_box` still searches outward, but when a real box exists on BOTH sides it returns the LINEAR INTERPOLATION of the two, weighted by relative distance (`t = back_dist / (back_dist + fwd_dist)`) — a tied `"| 1"` space now reads as the MIDPOINT of pipe and digit, so EACH seam absorbs roughly half the gap instead of one absorbing all of it (measured worst case 4.0px, both seams near-symmetric), and a flanked run sweeps smoothly with no privileged flip column (every step's magnitude bounded by its neighbours, not one dominating). When only ONE side has real ink (column 0; the tail of a run with nothing real beyond it), the blend degenerates to that single box exactly as round 2 already returned, so the literal-adjacency fixtures stay byte-identical. **THE BAR IS MEASURED, NOT ASSUMED**: round 3 first measures the real GLYPH-TO-GLYPH adjacent-cell delta the product already ships between genuinely different letter classes (x-height/ascender/descender/capital/digit/punctuation/ligature — transitions nobody has filed as a bug) — median ~5.5–6px, worst 14.0px (`digit`→`punctuation` on Bombora/Mopoke/Galah) — and holds every glyphless seam to that SAME empirical ceiling rather than an assumed constant. Laws: `glyphless_seams_stay_within_the_products_own_accepted_glyph_to_glyph_bar` (the bar itself, the `"| 1"` both-seams fixture, the symmetry mechanism claim) and `interior_run_between_two_different_letters_has_no_flip_step` (the 4+-run, no-step-dominates claim) in `caret_transition_item105.rs`; both proven non-vacuous against round 2's hard-pick code.
- **THE WRAP-BOUNDARY TRAP — caret transition claims are measured ROW-RELATIVELY, never absolute (adjudicated 2026-07-26).** A run of spaces long enough to fill an entire wrapped visual row by itself — flanked above and below by real-ink rows of the SAME logical line — forces `nearest_row_raster_box` (bounded to the caret's OWN row by design, an O(row-width)-not-O(doc) tradeoff) to come up empty on both sides, so `caret_cell_vertical` falls to the SYNTHETIC tier-3 box anchored to THAT row's own baseline. Two independent audit passes measured the caret's ABSOLUTE pixel position stepping across that row's wrap boundary and reported a ~30px jump as a HIGH-severity defect; it wasn't one. Crossing a soft wrap moves the caret down exactly one row's `line_height` and back toward the left margin — correct, INTENDED behaviour — and an absolute-position delta cannot distinguish that row-pitch component from a genuine cell-geometry discontinuity, because it compares two rows that are never drawn at the same y in the first place. Isolating the two (subtract each column's own `caret_baseline_y()` before diffing) showed the ~30px figure was ~84% pure row pitch (a flat 32.00px on every proportional world, exactly this fixture's `line_height`); the genuine tier-2/tier-3 boundary residual is 5.85px worst-case (Bilby) — comfortably inside `TRANSITION_BOUND_WIDE_PX` (7.5px) and well under the roster's own empirically-measured 14px glyph-to-glyph worst case. Any future caret-transition claim across a wrap must diff row-relatively (this column's `cy` minus its OWN row's baseline), not the raw absolute `cy`, or it will re-derive this same false positive. Law: `caret_transition_item105.rs`'s `glyphless_row_transition_is_bounded_row_relatively_across_a_wrap` — sweeps every adjacent column pair of the reported fixture over the full proportional roster, asserting BOTH that the absolute delta is genuinely large (proving the fixture reproduces the reported jump) AND that the row-relative residual at the same seam stays bounded.
- Laws: `render/tests/caret_ink_box.rs` — the ink-box hug across ascender / x-height / descender with the pad asserted letter-INDEPENDENT (and the pre-fix gap asserted as a fixture witness), a no-wildcard `CaretMode::ALL` form sweep, the mono uniform-grid law (one top y at every column on Tawny + Mangrove), the moving-streak law, the glyphless space/EOL/line-start fallbacks (now asserting the item-105 baseline-relative formula on a proportional world, the old row-box formula unchanged on mono), the pad-vs-dilation bound, and a grep-law that `render/layers.rs` holds no caret vertical geometry of its own. **`render/tests/caret_transition_item105.rs`** — the ADJACENT-COLUMN transition law item 91 never wrote: outer cell `(center_y, height)` diffed between an on-glyph column and its glyphless/ligature neighbour, over the full proportional-world roster, every representative glyph class (x-height/ascender/descender/punctuation/digit/capital/ligature/space/EOL/empty-line) at LITERAL adjacency, Block and Morph at rest (with Morph's travel proven UNAFFECTED, swept over the same roster), a wrapped-line boundary, two zooms (including a non-1.0 value) and 1x/2x DPI, the theme-preview-lag seam (both the empty-buffer arm-gate law and the repair round's real-row ratio-consistency law), plus the mono complement (must stay exactly zero) — every sweep carries its own non-vacuity proof against the pre-105 formula, and the repair round's own additions are separately proven non-vacuous against the FIRST (flawed) landing, `12c2fb4`.

## Theme capabilities as data (`theme/model.rs::RenderCaps`)

- Render call sites never branch on world identity — they read a `RenderCaps` field: `selection_style`, `caret_block_style`, `backdrop`, `elevation`, `decorative_wash`, `image_reveal`, `highlight_texture`, plus the personality fields `card_anchor`, `chrome_face`, `motion`, `list_style`, `facet_style` (and `TitleStyle::Placard{corner,scale,ink}`). Born as the Wagtail refactor ("default = every other world"); that framing is dead — 16 worlds now, and many set fields away from default (Firetail: placard BL 4.5/Bold + `chrome_face` Named("Archivo Black") + Bordered elevation; Galah/Magpie/Mangrove/Firetail: `list_style` Bars + placards; five worlds TopLeft `card_anchor` (Cassowary + Mangrove now `TopRight` — the item-45 fable picks) while default flipped TopCenter; lava worlds `motion` calm). **No theme may need its own code path** — new personality = new caps field + data.
- **ITEM 70's PRINTED-CARD caps** (`card_texture: CardTexture::Flat|HalftoneDots{angle_deg,cell_px,density}`, `card_shape: CardShape::Rectangular|Chamfered{cut_px}`) — Quokka alone assigns `HalftoneDots` (+ `Chamfered`). Read by the ONE `ListBacking::Card` consumer (`render::chrome::TextPipeline::card_shape_texture`, called from `prepare_panel_card_elevation` + `overlay_draw_card`'s spell-popup arm): a plain `sd_round_rect` SDF (`shaders/selection.wgsl`) gets replaced by `sd_card_rect`'s CSG intersection with a diagonal half-plane when `chamfer > 0`, shared by the fill/border/shadow trio so the eight-edge boundary agrees across all three; the texture composites only over the FILL, sampled at the ABSOLUTE canvas pixel (not instance-local) so a Split Pane's two surfaces share one continuous phase across the open gap — Quokka's dot lattice with a pure horizontal rolloff (`halftone_rolloff`) keeping the left content column clear. The texture's own ink is DERIVED (`theme::card_texture_ink`, a `muted`→`base_300` blend) — never a raw/amber literal in the cap. `render::chrome::narrowed_chamfer_px` caps the chamfer at 40% of a card's own smaller dimension so a genuinely tiny surface (the spell popup) never lets the cut steal text room, while an ordinary short query bar stays untouched. Dev-only gallery knob `AWL_CARD_CAPS_FORCE=flat|halftone` (Quokka), mirroring `AWL_CJK_FORCE`'s "total no-op unless set" contract. (**Item 71** briefly extended this with a SECOND card texture, `CardTexture::JaggedWave{tiers,period_x,period_y,amplitude,density}` — Bowerbird's own woven printed-card identity, sharing `dot_color` with `HalftoneDots` via `SelectionPipeline::set_wave` — plus an `AWL_WAVE_FORCE` capture knob. **Item 86's light-worlds taste round retired the whole variant**: Bowerbird's summoned cards returned to plain flat, `JaggedWave` had zero remaining assignees, so it — and `set_wave`, `CardWave`, `CardTextureDraw`, the WGSL `jagged_wave_*` functions, and `AWL_WAVE_FORCE` — were all cut outright rather than left as dead code nothing constructs. `CardTextureDraw` (once a two-variant wrapper enum) collapsed back to a bare `Option<CardHalftone>`.)
- **ITEM 86's ZIGZAG margin ground, TILED INTO A FIELD BY ITEM 89** (`theme::Background::Zigzag{from,to,dir,tint,period_px,amplitude_px,angle,density}`, shader id 7) — a tiled field of repeating chevron ("V") rows over the gradient, in the SAME whisper-mark family as `Dots`/`Pinstripe`/`Starfield` (composites through the shared `pattern_coverage` → `fs_main` mix pipeline, unlike `Bands`/`Waves`' own final-color branch). Quokka's old dot grid and Gumtree's old grass-`Bands` field BOTH moved here, each with its OWN authored dials so the two never read as a recolor of one asset: `period_px` is the TOOTH-WAVELENGTH dial (Quokka 100px, tight; Gumtree 170px, broad), `amplitude_px` the PROFILE dial (Quokka 24px; Gumtree 60px — and, through item 89's abutment rule, the field's ROW PITCH and the stroke's own thickness), `angle` the DIRECTION dial (Quokka ~54° steep diagonal; Gumtree ~15° near-horizontal), `density` the CONTRAST dial stacked on the shared `PATTERN_MAX_COVERAGE` ceiling (Quokka 0.60, bold; Gumtree 0.20, quiet). One shader function (`pattern_coverage`'s `shader == 7u` branch) reads all four via the SAME `params` vec4 slots Dots/Stripes/Bands already reuse per-shader (`params.x`=period, `.y`=angle, `.z`=amplitude, `.w`=density) — no new uniform layout, no per-world code path. `Background::Bands` is now DORMANT reusable infrastructure (Gumtree was its one assignee) — the exact "ships with zero worlds until one wants it" shape `edge: true` Dots already held. Laws: `render/tests/backgrounds_item86.rs` (the round's DESIGN brief — roster, four-dial distinctness, real-pixel contrast), `theme::tests`' data-level roster + palette laws. **ITEM 89 — the FIELD fix (correctness, not a new taste round), in TWO parts.** *(a) The FOLD.* The `shader == 7u` branch computed `center` from the ALONG-travel coordinate alone and took `abs(ry - center)`, which is ONE continuous chevron curve embedded in the plane: teeth repeated along travel, nothing repeated the curve ACROSS it, so a margin carried a single wandering stroke with large blank areas (62% of a tall Gumtree margin, the right two thirds of a Quokka one, measured at literally zero ink) and a taller window gained no second row — it only let the same stroke travel further off-canvas. The fix FOLDS the across-travel coordinate through a row pitch (`d = |fract((ry - center)/row_h + 0.5) - 0.5| * row_h`), turning the single curve into the family `center + k*row_h` — a genuinely tiled field. *(b) The ABUTMENT RULE — the coverage repair.* The fold's first cut set `row_h = period_px` (a square lattice). That TILES but does not COVER: row `k`'s ribbon only ever visits `ry` in `[k*row_h - amp - t, k*row_h + amp + t]`, so whenever `2*amp + 2*t < period_px` the field carries a hard BLANK LANE of `period_px - 2*amp - 2*t` that no chevron enters at any point of the plane — ~70px every 250px on the dials that first shipped, and at ordinary-but-shorter windows a narrow margin could sit wholly inside one (verified at the app's real adaptive column geometry: an 80x182px band of a 1600x600 Gumtree right margin, and a 27x234px cell of a 1400x700 left margin, at exactly zero deviation; Quokka's finer field was clean at every size). `row_h` is now `2.0*amp + thickness` (`theme::Background::zigzag_row_pitch_px` is the host mirror), so each row's ribbon sweeps exactly its own lane and its CORE sweeps a lane plus `0.2*t` of overlap: rows ABUT for ANY dials at any angle — coverage stopped being a property of the dial pair and became a property of the shader. (**Item 100** corrected that claim's scope: it read "any viewport size or aspect" and that clause was false — a viewport is a ROTATED RECTANGLE of the plane, so it inherits the guarantee only while it holds a whole tooth of travel; a `period_px: 2000`/`amplitude_px: 150` field on a 1200x800 canvas leaves a measured 78px lane. Bounded by the TOOTH, which `ZIGZAG_MAX_ROW_PITCH_PX` does not bound; no shipping world is within 4x, and that ratio is now the authored guard.) The old amplitude-vs-period collision clamp retired with it (abutting rows cannot smear). `period_px` is now the TOOTH wavelength alone; `amplitude_px` carries the profile, the pitch and the thickness. Dials: Quokka 100px/24px UNCHANGED (its field already covered every margin cell at every swept viewport), Gumtree 170px/60px — the same ~0.35 profile ratio item 86 authored (85/250), the whole field scaled to a pitch a page margin can hold. Recorded cost: Gumtree reads ~6 broad rows down an ordinary window where the first cut read ~3, and that reading is NOT recoverable — a void-free chevron's teeth span its own pitch by construction, so "rows three times the height of their own teeth" and "no blank lane" are mutually exclusive; broadness now lives in the tooth wavelength, the 2.5x pitch ratio against Quokka, and the low density. The draw call is still the LITERAL `pass.draw(0..3, 0..1)` fullscreen triangle (a handful of added fragment ALU ops; zero CPU work, zero new uniforms). ## The scene planner (`render/plan/`) — item 174

- **ONE deterministic, device-free layout stage between the measured inputs and the GPU.** It consumes the `ViewState` projection (the pipeline's `overlay_*` mirror), the already-resolved card box, the overlay row pitch and the grouped display-line sequence, and emits INSPECTABLE primitives plus INTERACTION geometry: one `PlannedRow { display, item, top, height }` per candidate DISPLAY LINE, `row_at(px, py)`, `display_at(py)`, `selected_display()`, `content_rows()`/`footer_top()`. It shapes nothing, measures nothing, reads no clock and touches no wgpu — so presentation decisions are assertable without a device (`render/plan/tests.rs`).
- **THE FORWARD `row -> y` ARITHMETIC AND ITS INVERSE ARE PRIVATE TO `plan/overlay_rows.rs`.** `overlay_row_top`, `overlay_row_of` and `overlay_row_index` are gone from `render/chrome`: a consumer cannot re-derive a row's position, only read it off the plan the pixels came from. Held by `render/tests/overlay_plan_law.rs`'s `only_the_planner_derives_an_overlay_row_position` — sentinels for the retired call names, `header_rows as f32`, AND for stepping off the band origin (`first_top` × a row count), which is the shape that hid `livingband::covered_rows`' own grid and the footer plate's seat for two years.
- **Routed through the one plan** (built once per overlay frame in `prepare_overlay`, threaded down): the pointer hit-test (`overlay_row_at`), the range rails (draw + hit), the visual-selection transaction's band target and coverage grid, the Pane band, the `Bars` plates, the chord plates, the footer plate, the slant text-clip bands, the shaped rows' item mapping, and the sidecar's `overlay.window` report. - **The inverse SCANS the planned slots, it does not invert the formula.** `(py - first_top) / lh` truncated at a row's own first pixel lands on the row ABOVE whenever `k * lh` is not exactly representable (found at `lh = 12`, `header_gap = 63.55`, row 11). Comparing against the same `f32` tops the band was drawn from cannot disagree with the draw. O(visible) over at most a couple of dozen rows.

## Picker hover/click stability + movement latency (`app/input/mouse.rs`, `overlay/nav.rs`, `probe.rs`)

- **THE REAL-MOTION HOVER GATE (item 85).** A theme-picker world jump previews the destination world's rail/size/type/material immediately (reanchor, Pane↔Bars, a settling font reshape) — but that re-layout must never itself read as a pointer gesture. `OverlayState::hover_at(px, py, hit)` is the ONE door `app/input/mouse.rs::overlay_hover` calls on every `CursorMoved` (real travel or a platform-synthesized duplicate at the identical coordinates): it compares `(px, py)` against `OverlayState::last_hover_px` and only re-hit-tests/re-selects (`hover_select`) when the pointer's own PHYSICAL position genuinely changed since the last check — a hit-test RESULT changing on its own, with the pixel unmoved, is a no-op. Pure and GPU-free (`hit` is a caller-supplied `Option<usize>`, not a pipeline call), so it's unit-tested directly. Laws: `overlay::tests::hover_at_gates_on_real_pointer_motion_not_a_relayout_hit_test_change` (proves BOTH that the hazard is real — an ungated `hover_select` really does cascade — and that the gate refuses it), `overlay::tests::hover_at_off_a_row_records_position_without_selecting`, `render::tests::overlay_hover_stability_law` (the same hazard against real pipeline geometry: a deliberate Wagtail→Cassowary rail crossing moves what a stationary pixel hits). Keyboard nav is untouched (`move_sel(±1)` still advances exactly one visible row per press, hover's own bookkeeping never leaks into it — `overlay::tests::keyboard_advances_exactly_one_visible_row_per_press_even_after_a_hover`).
- **THE MOVEMENT-SLOP WIDENING + KEYBOARD BASELINE (item 106).** Item 85's gate closed EXACT-pixel duplicates, but left a hazard the exact-equality check couldn't see: a list WINDOW SCROLLING under a genuinely resting pointer (a real keyboard `move_sel` deep enough to shift the candidate window) changes which row a stationary pixel hits, and any real `CursorMoved` past that point — even a single physical pixel of a resting hand's ordinary hardware jitter — used to steal the keyboard's own selection outright. `hover_at` now gates on SQUARED DISTANCE against `HOVER_MOVE_SLOP_PX` (private to `overlay::nav`, one owner; 4.0px, matching `app::DRAG_ARM_SLOP_PX`'s identical "content relocating under a stationary pointer" precedent) rather than bare inequality — real travel PAST the slop still takes over on the very first such event, no added latency, no dead zone; the anchor is STICKY below the slop (stamped forward only on a reported move) so a genuinely slow drag still crosses the threshold from its original anchor rather than re-basing itself every sub-slop increment. The OTHER half: `OverlayState::arm_hover_baseline(px, py)` re-anchors the gate to the pointer's CURRENT resting position, called by the shared keyboard-dispatch seam (`App::apply` live, `ReplaySession::apply_chord` headless) after every keyboard-driven action, AND by `App::overlay_wheel` — the mouse wheel drives `move_sel` exactly like ↑/↓ (a second "deliberate crossing" input class, same as the keyboard) but is dispatched straight from `on_mouse_wheel`, never through `apply`, so it stamps the baseline itself rather than relying on `apply`'s stamp — without either stamp, a session with no prior hover (`last_hover_px` still `None`) would let the pointer's first incidental `CursorMoved`, however small, read as unconditional motion under `hover_at`'s own cold-start rule and hand the selection to wherever a motionless hand happens to rest. `HOVER_MOVE_SLOP_PX` is now a re-export of `app::DRAG_ARM_SLOP_PX` itself (not a second `4.0` literal), so the two gates cannot drift apart under a future retune of either. Laws: `overlay::tests::hover_at_movement_slop_boundary_law` (the threshold in both directions, pure distance), `overlay::tests::keyboard_baseline_stamp_protects_a_pointer_that_was_never_explicitly_hovered` (non-vacuous: proves the unstamped scenario steals first), `overlay::tests::keyboard_nav_survives_a_pointer_parked_over_any_row_relative_to_the_destination` (row above/below/far/landing), `overlay::tests::hover_movement_slop_gate_holds_across_every_overlay_kind_no_wildcard` (the full `OverlayKind` roster via a compile-time-exhaustive match — the sweep still iterates the hand-kept `OverlayKind::ALL` roster, not the match itself; a variant added to the enum and the match but forgotten in `ALL` still compiles clean and silently skips the sweep, a limitation `OverlayKind::ALL`'s own doc discloses), `render::tests::hover_slop_law` (the same hazard against real pipeline geometry, swept across `Pane`/`Bars` and 1×/2× DPI), `app::input::tests::wheel_scroll_from_cold_start_does_not_expose_selection_to_the_next_hover_check` (the wheel path specifically, non-vacuous: proves the unstamped `overlay_wheel` steals first). **The pointer-replay seam:** `TextPipeline::resolve_overlay_hover` is the ONE hit-test-then-`hover_at` seam both `App::overlay_hover` (live) and `ReplaySession::apply_move` (headless, via `capture::OraclePipeline::resolve_overlay_hover` + `sync_overlay`, which pushes the CURRENT overlay's row/window geometry onto the otherwise buffer-only motion oracle) route through — proven end-to-end through the real `--keys` replay engine by `run::tests::item_106_pointer_replay_seam_reproduces_a_keyboard_scroll_stealing_a_stationary_pointer_check`. `apply_move`/`sync_overlay` are NOT yet wired to the `--keys` CLI STRING grammar (no `move X Y` token) — only reachable by constructing `ReplaySession` directly, as that law does — and cover the flat/list picker geometry path only (not the Theme picker's faceted `overlay_lens`/section-header layout).
- **THE ONE CLICK-ACTIVATION RULE.** `App::overlay_click` fires ONLY on `ElementState::Pressed` (never `Released`) and hit-tests `self.cursor_px` at that same instant — so "the row a click activates" is unconditionally the row under the PRESS, never a release position or whatever an earlier hover last computed. No separate release-time re-evaluation exists.
- **MOVEMENT-LATENCY, the live companion to offscreen `--bench-theme-burst` (item 85).** `App::retint_theme_preview` — the ONE owner every input kind (keyboard nav, mouse hover, mouse wheel) funnels a theme-picker world change through — arms `probe::mark_movement_input()` right before the real relayout work; `Gpu::redraw` closes it out against the frame it actually PRESENTS via `probe::note_presented_frame()`, at the exact point the existing `"present"` trace fires. `probe::latency_distribution()` reports count/min/p50/p95/max in ms. Reads through the SAME `probe::recording()` gate (both the automated `--live-script` probe and the user's `AWL_FLIGHT_RECORDER`) every other diagnostic trace point uses — no new shared live/headless driver. Native-only; a no-op on a plain launch (the clock is never even read). Laws: `probe::tests::movement_latency_mark_and_present_produce_a_sample_and_distribution`, `probe::tests::movement_latency_is_a_no_op_outside_recording`, `probe::tests::parse_covers_the_latency_step`.
